## 二、Playwright vs agent-browser 技术选型对比

| 评估维度 | Playwright (Node.js 原生 API) | agent-browser (CLI 工具) |
|---|---|---|
| Windows 本机兼容性 | 优秀，直接复用本地 Chromium 缓存 | 本机未安装，需额外包装进程 |
| 独立配置目录与多平台隔离 | `launchPersistentContext(profileDir)` 原生精准隔离 | 需通过命令行参数间接转发 |
| 后台长期定时调度与任务锁 | 进程内直接持有 `BrowserContext` 句柄，支持进程级互斥锁与超时回收 | 多一层 CLI 子进程调度，锁与句柄回收复杂 |
| 静默无界面 / 可见登录窗口切换 | 通过 `headless: true / false` 即时切换 | 需额外启动不同会话 |
| 技术栈统一性 | 与后端 Fastify + TypeScript 完全统一，内存开销最低 | 额外引入中间层复杂度 |

**最终选型结论**：采用 **Playwright (Node.js API)** 作为唯一浏览器自动化引擎，不引入额外的 `agent-browser` 中间层，以保持长期后台运行的稳定性、低内存占用和清晰的生命周期控制。

## 三、独立浏览器隔离与持久化实测结果（`tests/verify-browser-isolation.mjs`）

- **无界面启动**：成功调用本地 `chromium-1254` 启动独立上下文（`headlessLaunch1: true`）。

- **多目录隔离**：创建另一配置目录 Profile B 访问同站点，确认未读取到任何 Profile A 的 Cookie 或 LocalStorage。
